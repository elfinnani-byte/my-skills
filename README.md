# 바이브 코딩 스킬 모음 (my-skills)

프로젝트를 **기획 → 개발 → 디자인 → 배포** 순서로 진행할 때, 각 단계에서 반복적으로 하던 작업을 Claude 스킬로 만들어 모아둔 저장소입니다. 팀별 에이전트를 구성할 때 폴더 단위로 바로 활용할 수 있습니다.

## 폴더 구조

```
my-skills/
├── 00-공통/       전 단계에서 공통으로 쓰는 스킬
├── 01-기획/       프로젝트 기획·설계 단계
├── 02-개발/       실제 코드 작성 단계
├── 03-디자인/     UI/UX 디자인 단계
└── 05-배포/       배포 전후 단계
```

## 스킬 목록

| 단계 | 스킬 | 하는 일 |
|---|---|---|
| 00-공통 | `session-handoff` | 세션 종료 시 핸드오프 문서 자동 작성 |

| 01-기획 | `doc-consistency` | 여러 기획 문서 간 정합성 교차 검증 |

## 00-공통

### session-handoff
**🚨 Before**: Claude Code로 오래 작업하고 나면, 다음에 이어서 할 때 뭘 했는지, 뭘 결정했는지, 뭐가 남았는지 기억이 안 나서 처음부터 대화를 다시 훑어봐야 했습니다.
**✨ After**: 세션이 끝날 때(또는 길어질 때 먼저 제안받아) 진행상황·결정사항·변경 파일·다음 TODO가 정리된 핸드오프 문서가 자동으로 남아서, 다음 세션이 바로 이어집니다.

### doc-polish
**🚨 Before**: 마크다운으로 정리한 기획 문서를 팀에 공유하거나 인쇄할 때마다 서식을 일일이 손봐야 했고, Word나 PDF, HTML로 바꾸는 것도 매번 번거로웠습니다.
**✨ After**: 원하는 형식(md/Word/PDF/HTML)만 말하면 내용은 그대로 두고 서식만 깔끔하게 다듬어줍니다. HTML은 카드형 레이아웃과 절제된 톤의 콜아웃 박스 스타일로 통일됩니다.

## 01-기획

### project-kickoff-scaffolder
**🚨 Before**: 새 프로젝트를 시작할 때마다 CLAUDE.md, PRD, 설계서를 매번 처음부터 구조 잡아 작성하느라 시간이 걸렸습니다.
**✨ After**: 프로젝트 소개·타겟·핵심기능·스택만 알려주면 3개 문서를 표준 템플릿(Mermaid 다이어그램 포함)으로 한 번에 만들어줍니다.

### db-schema-rls-reviewer
**🚨 Before**: Supabase 테이블을 설계할 때 RLS 정책을 빠뜨리거나 너무 넓은 권한을 주는 실수를 나중에야 발견하곤 했습니다.
**✨ After**: 설계서의 테이블·컬럼 설명만 봐도 정규화·인덱스·FK 문제와 RLS 누락·과도 권한을 짚어주고, 바로 쓸 수 있는 수정 예시(SQL)까지 제시합니다.

### doc-consistency
**🚨 Before**: PRD, 설계서, CLAUDE.md처럼 여러 문서를 동시에 관리하다 보면 버전·용어·다이어그램이 문서마다 조금씩 어긋나 있는 걸 나중에야 발견했습니다.
**✨ After**: 여러 문서를 한 번에 교차 검증해서 프론트매터·용어·다이어그램·요구사항 불일치를 유형별·심각도별로 짚어줍니다.

## 02-개발

### commit-summary
**🚨 Before**: 매번 코딩 작업이 끝날 때마다 내가 어느 부분을 고쳤는지 일일이 찾아봐야 했고, 팀 규칙(`[범위] 한 일 (#이슈)`)에 맞춰 요약하려니 번거로웠습니다.
**✨ After**: 스킬 한 번이면 변경된 코드를 확인하고 팀 규칙에 맞는 커밋 메시지로 요약해줍니다.

### debug-session
**🚨 Before**: 에러가 나면 재현 방법을 정리하고, 원인을 추적하고, 수정하는 과정을 그때그때 감으로 진행하다 보니 중요한 단서를 놓치곤 했습니다.
**✨ After**: 문제 확인 → 재현조건 좁히기 → 원인 추적 → 근본원인 진단 → 수정안 → 재발방지책까지 체계적인 순서로 디버깅을 진행합니다.

### git-branch-strategy
**🚨 Before**: 기능을 여러 개 개발할 때 브랜치를 어떤 순서로, 어떤 이름으로 만들지 매번 고민했습니다.
**✨ After**: 설계서 기반으로 기능 간 의존관계를 파악해서 `feature/edu`처럼 짧은 이름과 개발 순서를 바로 제안해줍니다.

## 03-디자인

### style-guide
**🚨 Before**: 프로젝트마다 색상·타이포그래피·간격이 은근히 제각각이라 화면마다 미묘하게 톤이 달랐습니다.
**✨ After**: 기존 코드베이스를 스캔하거나 새로 정의해서 스타일 가이드 문서를 만들어두고, 이후 모든 화면 작업의 기준으로 삼습니다.

### screen-design-new
**🚨 Before**: 새 화면을 만들 때마다 레이아웃과 컴포넌트 구성을 처음부터 고민했습니다.
**✨ After**: 화면 목적만 알려주면 스타일 가이드 기준으로 shadcn/ui 컴포넌트를 활용한 레이아웃을 접근성·반응형까지 고려해서 제안해줍니다.

### screen-design-review
**🚨 Before**: 화면을 다 만들고 나서야 색상이나 간격이 다른 화면과 미묘하게 다르다는 걸 발견했습니다.
**✨ After**: 완성된 화면을 스타일 가이드 기준으로 점검해서 일관성·접근성·반응형 문제를 [항목/문제/수정 제안]으로 정리해줍니다.

## 05-배포

### deploy-checklist
**🚨 Before**: 배포 전에 환경변수나 마이그레이션을 빠뜨리는 실수도 있었고, 변경사항이 다른 기능에 영향을 줄지 확신이 안 설 때가 많았습니다.
**✨ After**: 환경변수·빌드·마이그레이션 체크리스트와 함께, git diff를 분석해 회귀 위험이 있는 부분을 위험도별로 미리 짚어줍니다.
